# Clean-room provenance rules

The objective is an independently authored DockBridge USB-display
implementation. “Different enough” is not a design or legal test. Compatible
behavior may be equivalent, but implementation expression must be original and
each protocol fact must have a reviewable, lawful source.

This repository is not currently evidence of a formal two-team clean-room
process. Its maintainers previously inspected a compiled vendor package for a
security audit. Consequently, a strong commercial clean-room claim would need
separate protocol observers and implementers, written specifications, access
controls, and legal review. This document establishes the boundary used for the
open research code; it does not provide legal advice.

## Admissible inputs

- public USB descriptors and standards;
- public Apple APIs and documentation;
- public, license-compatible research with attribution;
- black-box behavior observed on lawfully owned hardware where applicable law
  and agreements permit interoperability research; and
- synthetic fixtures created specifically for this repository.

Every non-synthetic protocol fact should record its origin, observation date,
hardware VID:PID and revision, experimental conditions, and whether it was
independently reproduced. Facts should describe externally visible behavior,
not a vendor routine or data structure.

## Excluded inputs and outputs

- copied or translated vendor source, decompiled pseudocode, assembly-derived
  implementation structure, private symbols, or proprietary log strings;
- vendor binaries, resources, firmware, cryptographic keys, certificates,
  protected-media material, or extracted tables;
- screen pixels, user data, device serials, monitor serials, or machine paths;
- payload captures in the public repository before provenance and legal review;
  and
- code generated by asking a model to paraphrase proprietary code.

The public observation format therefore accepts metadata only. It records
transfer order, direction, transfer type, endpoint, and length, but rejects a
payload field. Private raw research material should live outside this Git
checkout and must never be used as a source-code template.

The activation-envelope format adds capture-relative timestamps and four
experiment markers but preserves the same boundary: no payload, control setup
packet, semantic command label, key, or screen data. Completed `.dba` files are
ignored private artifacts. A synthetic envelope tests the parser; a black-box
envelope is evidence only for its recorded metadata and becomes a public fact
only after the repeat/review criteria in `ACTIVATION-ENVELOPE.md` are met.

## Implementation rule

Write new code from a reviewed behavioral specification and USB standards.
Prefer different abstractions selected for this project’s safety requirements:
bounded parsers, explicit state transitions, exact hardware allowlists,
memory-safe codec components, fake transports, deterministic tests, and no
networking or persistence. Do not preserve vendor naming, file layout, control
flow, constants, or data structures merely because they appeared in a binary.

Before enabling a real USB write, require:

1. a provenance entry for every field and state transition;
2. parser and fake-dock tests, including malformed and disconnect cases;
3. fuzzing of every externally controlled length and record type;
4. an exact VID:PID/revision and endpoint allowlist;
5. a no-firmware-flashing invariant; and
6. review by someone who did not derive the implementation from proprietary
   code.
